## 一、总体评价

这是一个工程纪律明显高于同期阶段项目的量化交易仓库：6 天内 42 次提交，`docs/DEV_PLAN.md`
维护得像活文档，测试 110/110 全绿，`ruff` 零警告。数据/结算规则的实证方法论（578 窗口
+ Binance 交叉验证、taker fee 官方双源确认）扎实程度超过大多数早期个人量化项目。

项目当前的资源投入方向是：**深耕 5 分钟 BTC/ETH Up/Down 冷门方策略（`crypto_5m`）**，
`PROJECT_PLAN.md` 中规划的互补套利 / NegRisk / 关联市场 / 跨平台等策略仍是空目录。这是
一个已经明确的方向选择，本报告不再讨论是否切换赛道，而是聚焦如何在现有方向上把胜率和
过滤逻辑做扎实。

## 三、代码结构问题与建议

### 值得保持的设计

- `strategies/crypto_5m/decisions.py` 把判定逻辑抽成纯函数（无 I/O、无时钟），实盘
  orchestrator 与回测引擎调同一套函数，避免"两套逻辑漂移"——这是量化系统最容易被忽视
  的一致性问题，处理得很好，**后续新增动量/特征过滤逻辑应延续这个模式**（见 5.4）。
- `execution/broker.py` 的 `Broker` Protocol 把 live/paper 抽象成同一接口，`orchestrator`
  完全不感知真实资金路径，干净的依赖倒置，值得继续沿用。
- `data/rtds.py` / `data/ws.py` 对"链路层活着 ≠ 业务频道在推数据"这类分布式系统的坑做了
  业务级看门狗，注释记录了踩坑教训，是好习惯。

### 需要改进的地方

1. **README.md 目录结构图已与实际代码脱节**：README 写的是顶层 `backtest/`，但回测引擎
   实际在 `strategies/crypto_5m/backtest/` 下（`446a128` 迁移）。`DEV_PLAN.md` 是同步的，
   README 没跟上，建议顺手修正。
2. **回测框架耦合在单一策略包里**：`engine.py`/`loader.py`/`metrics.py`/`report.py` 目前
   只服务 `crypto_5m`。如果后续要给 `crypto_5m` 增加动量特征的独立回测/特征分析管道，
   建议提前把"事件驱动回放"和"撮合/指标"这类与策略无关的部分抽成共享核心，特征/决策部分
   继续做成插件式纯函数（同 `decisions.py` 的思路）。
3. **`infra/config.py` 的私钥类型与文档承诺不符**：模块 docstring 写"所有密钥以 SecretStr
   持有"，但 `private_key` 等字段实际类型是 `str`（仅 `Field(repr=False)`）。目前代码里
   没有直接打印明文的地方，暂无实际泄露，但建议把类型改成真正的 `pydantic.SecretStr`，
   属于操作真实钱包私钥系统的基本防御纵深。
4. **`app/redeem.py` 硬编码了 `10**6`**（USDC 精度换算），而 `execution/chain.py` 里同样
   的换算是动态查询 `usdc_decimals` 完成的，两处不一致。风险不大但违反了项目自己"配置化
   管理、不硬编码"的第一条纪律，建议统一成动态查询。
5. **没有 CI**：仓库没有 `.github/workflows`，测试/lint 目前全靠手动跑。考虑到提交频率高
   （单日 18 次）且操作真实资金，建议加一个最小的"push 即跑 pytest + ruff"流水线，防止
   某次重构悄悄破坏 `decisions.py` 这个单一真相来源模块。

## 四、结算规则与回测数据分析

`docs/settlement-rule.md` 的方法论值得肯定：从 Gamma `description` 一手拿到结算规则原文，
用 578 个 Binance K 线窗口按"平坦度分桶"检验分歧结构是否符合预期（而非只看总体一致率），
taker fee 公式做了官方文档 + Gamma 字段双源确认。这个严谨度决定了后续回测结论的可信度
基础是扎实的。

### 已有回测结论摘要（`backtest-report*.md`）

| 实验 | 结果 | 意义 |
|---|---|---|
| 基线参数全量回测 | BTC 每笔 -$0.47 / ETH -$0.28（费后） | 名义胜率 31~34% > 隐含胜率 28~29%，但止盈 0.65 截获上限 + 手续费吃光毛优势 |
| 60 组网格 + walk-forward | 验证段无一组转正 | tp=0.99（持有到结算）方向最优，但仍是"亏得最少" |
| 27 组止损扫描 | 83% 持仓触发止损，全部反而更差 | 止损把本该结算赢的仓位提前砍掉，假设被证伪 |
| max_vol 现货波动过滤（b07） | BTC 减亏 54%（仍为 -$720） | 四轮实验里第一个"方向正确"的杠杆，值得继续深挖 |
| 根因 | 冷门方入场均价 ~0.27，盈亏平衡胜率需 27%，实际 23.5~25.1% | 定价劣势 2~4 个点，不是执行/调参问题 |

**这组结论对第五节的意义**：现有的价格区间 + 波动区间过滤（`max_entry`/`min_entry`/
`max_vol`）已经把"能想到的最直接的过滤维度"扫过一轮，且已经验证"参数平面内无解"。这意味着
接下来想靠过滤提升胜率，大概率需要**新的信息维度**（订单流特征、动量结构、跨币种联动等），
而不是在同一批参数上继续微调——这正是本报告第五节要展开的方向。

**数据口径提醒**：HF 数据集的 outcome 是推断值，目前只做了 30 个窗口的抽样核对（30/30
一致）。在把任何新特征的历史回测结论当作定论之前，建议把这个抽查样本扩大到几百个窗口。

## 五、执行策略优化建议：在现有方向内做深化

延续团队已经验证有效的方法论（实证优先、分桶检验单调性、walk-forward 防过拟合），
把优化目标从"调整现有价格/波动阈值"转向"引入新的过滤维度"。

### 5.1 先明确验证标准，再动手做特征

`max_vol` 过滤是一个很好的参照系：它把 BTC 亏损减少了 54%，方向正确，但依然是负数——
说明"过滤掉更差的窗口"和"把剩下的窗口变成正 EV"是两件不同的事。建议给新特征设一个
明确及格线：**在验证段（后 30%，从未参与特征筛选）的名义胜率需要清晰超过入场均价对应
的盈亏平衡胜率（当前口径下约 27%）**，而不是"比基线好一点"就采纳。这条线同样适用于用
人工经验转化出来的过滤规则（见 5.2）。

同时建议保持团队已有的纪律：**先列出要测试的候选特征清单，再看验证集结果**。候选特征
一多，总能在 14,000+ 历史窗口里"偶然"找到几个看起来有效的组合，这是过拟合/多重检验的
经典陷阱，`DEV_PLAN.md` 里"回测好看 ≠ 放大仓位"这句话本身就是对这个陷阱的提醒，建议在
特征工程阶段同样适用。

### 5.2 把"人工判断胜率高"系统化，这是目前最有价值的信息

人工交易胜率高、机械规则（`decide_entry`）胜率不高，这个差异本身就是一条有价值的线索：
说明人工判断时用到了当前 `decisions.py` 里没有编码的信息。建议：

1. 接下来的人工/半人工交易（或哪怕只是人工观察，不下单），在每次做出"进/不进"判断前，
   用固定格式记一笔：当时依据的是什么信号（比如"最近两个窗口方向一致"“盘口冷门方深度
   突然变大"“价格已经横盘一段时间”等），做成结构化标签而不是事后回忆。
2. 把这些标签逐条转成可计算的特征（见 5.3 给出的具体候选），拿现有的 HF 历史数据集
   （或积累中的 `pm-record` 实盘数据）回测这些特征本身是否真的带来区分度。
3. 在正式把某条人工经验写死进 `decisions.py` 之前，建议对自评"胜率高"保持一点谨慎：
   人工判断的自我评估容易受小样本、记忆偏差影响（赢的印象比输的深）。用固定标准
   **提前**记录（而不是选择性回顾），积累到跟团队现有统计口径一致的样本量（`DEV_PLAN.md`
   里用过的 p=0.5±0.05 需 ~384 笔的算法可以直接复用）之后再下结论。

### 5.3 动量/特征候选清单

可以在不改变现有策略骨架的前提下，作为 `decide_entry` 的**额外过滤条件**加入（类似
`max_vol` 现在的角色），建议的候选方向：

| 特征 | 说明 | 为什么可能有信息量 |
|---|---|---|
| TWAP 短窗斜率 | 最近 10~30s 的价格变化率（一阶导） | 比单纯 high-low range 更能反映"现在还在往哪边冲" |
| TWAP 二阶导（加速度） | 斜率是否在放缓/反转 | 趋势衰竭常是均值回归的前置信号，可能比现有 range 过滤更贴近"这局是否会翻盘"这个问题本身 |
| 盘口失衡 | 冷门方/热门方买卖档口量比 `(bid_size-ask_size)/(bid_size+ask_size)` | 反映短期买卖压力，`LocalOrderBook` 已有档深数据，改造成本低 |
| 价差/流动性质量 | 冷门方 bid-ask 价差宽度 + 深度 | 窄价差+有深度更接近"真实定价"，宽价差可能是噪声/流动性差导致的假信号 |
| Chainlink 更新频率 | 心跳间隔 vs 真实价格更新 | `crypto_5m_underdog.md` 里团队自己点名"波动过滤被操纵风险"是最脆弱的假设——喂价卡住会造成假的低波动读数，建议优先做这个特征去甄别 |
| 跨币种联动 | 同一时间窗口 BTC/ETH 结果的相关性 | 两者可能受同一宏观驱动，一个可以作为另一个的先验信号，用现成历史数据集即可检验，不需要新数据源 |
| 时段效应 | 亚洲/欧美时段流动性、基线波动率差异 | 用团队已经用过的"分桶 + 检验单调性"方法论，看入场时段本身是否对结算胜率有区分度 |
| 连续窗口自相关 | 上一窗口的方向/波动幅度是否预示下一窗口 | 直接检验"动量延续"还是"均值回归"哪个假设更符合数据，用 HF 历史数据的时间序列即可回测 |

### 5.4 工程落地建议

- 新增 `strategies/crypto_5m/features.py`，与 `decisions.py` 平级，保持同样的纯函数
  风格（无 I/O、无时钟），方便实盘与回测复用同一套特征计算。
- 扩展现有回测引擎，把入场时刻的特征向量 + 最终结算结果一并落盘（CSV/SQLite 均可，
  `pyproject.toml` 里已有 `numpy`，做数据分析可以直接加 `pandas`/`polars`）。
- 延续团队已经验证有效的"单变量分桶 + 单调性检验"方法论（就是 `backtest-report.md`
  3.1 节对 `take_profit` 做的那一套）：先看每个候选特征单独分桶后胜率/EV 是否单调，
  再考虑多特征组合，避免一上来就上黑箱模型——在单笔金额本来就很小、边际很薄的场景下，
  可解释的阈值规则比黑箱分类器更容易调试和信任。
- 只有在单变量过滤不够用时，再考虑简单的打分模型（如逻辑回归），并继续用现有的
  70/30 train/val 纪律验证，验证集需清晰超过盈亏平衡线才采纳。

### 5.5 数据源注意事项

HF 数据集是 2026-03~05 的历史微观结构，可能与当前市场不同，团队在 `b07` 报告里已经
指出"方向可迁移、数值需实盘标定"，这个原则同样适用于新特征：建议 `pm-record` 积累
一定量实盘数据后，把同一套特征逻辑在实盘数据上跑一遍一致性检验，与历史数据集的结论
做交叉对照，而不是直接把历史数据算出的阈值搬到实盘参数里。

## 六、其它细节问题

- **仓库公开性与内部文档的说法不一致**：无需任何凭证即可 `git clone` 这个仓库，说明
  它目前是公开的；但 `docs/conversations/README.md` 里写着"仓库当前为私有（Private）"，
  并提醒"提交前应确认对话记录中不含私钥"。如果仓库确实已经公开，`docs/conversations/`
  下的开发会话记录、以及 `backtest-report*.md` 里的策略研究结论，实际上是公开可见的。
  建议明确一下可见性设置是有意为之还是疏忽，并重新审查一遍会话记录内容。
- **`TickRecorder` 仍未接入实盘交易**：`trade5m.py` 本身不落自己的 tick 数据，`pm-record`
  是独立进程。复盘某笔真实交易当时的完整盘口上下文，目前需要靠时间戳手动对齐
  `runtime/logs/` 和 `pm-record` 的独立数据流，`DEV_PLAN.md` 阶段 2 已经列了这项待办。
- **早期提交信息**（"1"、"3次成交"、"签名3"等）信息量低，后期已切换成规范的
  `feat(scope): ...` 格式，是个好转变，无需处理历史提交。

## 七、优先级行动清单

1. **落地 SQLite 存储层 + 自动赎回闭环**（阶段 2）：进程重启会丢持仓，`pm-redeem` 在
   proxy 钱包（signature_type=3）场景下目前无法执行赎回——这是资金操作性风险，优先级
   高于任何策略优化。
2. **补齐风控最小集**（阶段 4）：每日亏损熔断、Kill Switch 文件检查、下单前余额检查，
   建议作为"把单笔金额从 $2 提高"之前的硬性前提。
3. **把人工判断信号系统化记录**（5.2）：这是目前信息密度最高、成本最低的下一步。
4. **搭建 `features.py` + 离线特征分析管道**（5.4）：从单变量分桶检验做起。
5. **给新过滤器定验证标准**（5.1）：验证集胜率需清晰超过盈亏平衡线，而不是"比基线好"。
6. **用 `pm-record` 实盘数据校准历史数据集结论**（5.5）：方向可迁移，数值需重新标定。
7. **代码卫生小项**：`SecretStr` 化私钥、统一 USDC 精度换算、补最小 CI、修 README 目录图。
